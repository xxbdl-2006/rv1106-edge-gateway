为什么这两条线只在 OSD 相交：传感器支线走自己的采样周期，视频支线走帧周期。 frame_ring 借出的缓冲是 const，所以 OSD 必须在私有副本上合成 —— 这条契约同时保证了「传感器慢」不会变成「视频丢帧」。

04

架构红线

破坏了会引入很难查的 bug —— 这几条是踩过坑换来的。

① socket 只许出现在一个文件里
只有 rtsp_server.c 碰 socket；协议解析在 rtsp_proto.c，RTP 打包在 rtp_h264.c。 这样它们都是纯缓冲、无系统依赖，Windows 上才有得测。
② 多客户端必须是 reader 单消费者
reader 打包一次 → 扇出。别改成「每客户端各自取队列」，那会让帧被瓜分，全员花屏。
③ handler 不得持锁调 client_send_response()
它自己会取 server->mutex，持锁调用直接死锁。
④ 借出的帧缓冲是 const
不能就地涂改 —— OSD 那条路径之所以合法，正是因为在私有副本上合成。
⑤ 主循环禁止会增长的动态分配
8 小时长稳的零泄漏就是这么保住的（RSS 钉死）。
⑥ SENSOR_SRC 不进 MEDIA_SRC
传感器与视频流水线刻意零交集 —— 两条线只在 OSD 相交。

实测数据与延迟归属

「延迟」是两个数，归属方相反 —— 旧记录里的「ffplay 约 0.75 s」两个都不是，已作废。

稳态管线延迟
帧已在流里之后		 ≲ 50 ms 网关。两处队列峰值深度均为 1（1020 帧 @ 30.000 fps、零丢帧）→ 排队 ≤ 1 帧 = 33 ms；TCP 建连 19 ms；ping < 1 ms。

按下 PLAY 到看见画面		 1.12 – 2.12 s
中位 ≈ 1.5 s		 前半段网关：joining 门控 —— 等下一个 IDR 才发首包（否则观众拿到花屏）。关键帧间隔实测恰为 1.000 s，故为 0–1 s 抽奖。后半段 ≈ 1.1 s 在客户端，nobuffer 类开关反而更慢。
帧间隔33.3 ms 均值 300 帧 9.000 s，漂移 −1.4 ms → 固定延迟而非累积。p50 21.6 / p95 68.2 ms 是 RTP over TCP 交织（一个 TCP 段带多帧），不是抖动。
IMU 轮询间隔100 ms 一次 14 字节突发实测 ≈ 28 ms；30 fps 的每帧预算 33 ms。100 ms 档 → 29.998 fps / 零丢帧；10 ms 档 → 21.4 fps / 丢 122 帧。
冷启动到出流≈ 19 s 接管本身 14 s（含等厂商链 ~4 s）。旧的「11 秒出流」测的是不可靠路径，已作废；旧代码在冷启动下永不出流。
8 小时长稳864,001 帧 30.00 fps · drop 0 · dup 0 · exit 0；fds 24 / threads 6 全程不动，末 2 小时 RSS 增长 0 KB。
网络中断 20 sPASS 网关 pid 不变、不泄漏、编码不停；死会话被回收后新客户端可连。代价：原客户端扛不过中断、需重连 —— 这是设计取舍，不是缺陷。
